# 設計(DESIGN)

このプロジェクトを「どう作るか」を書く文書です。「何をするか」は [SPEC.md](SPEC.md) に書きます。

## 書式の見本

```
## 節の名前

- 決まっている作り方(関係する D 番号があれば書く)
```

検討中の論点は次の書式で書きます。

```
### 論点の題名

- 状況:何が決まっていないか。

```

### 計算本体と画面の分け方

- 計算本体は「状態」と、それを変える関数(`update` で時間を進める、`tap` でタップする)だけを持つ。時計や画面には触らない。
- 画面(`src/ui/main.js`)は、ブラウザの描画のたびに描画の時刻を窓口(`src/ui/session.js` の `advanceTo`)に渡し、状態を読んで描く。窓口は、メニューを開いている間は時間もタップも計算本体に渡さない(D-134)。
- こうすると、テストでは時間を好きなだけ早送りでき、同じシードで同じ結果になることを確かめられる。
- 演出(`src/ui/effects.js`)は、計算本体の結果(`game.results`)を読むだけで、書き換えない(D-051)。
- 進み具合(ウロコイン・魚ごとの鱗・竿の段階と工程・釣れた魚)は `game.progress` にまとめ、保存とセーブコードはこれだけを対象にする。
- 強い魚とのやりとりの途中の状態(体力・制限時間・今の命中範囲・ミニゲームの系統の乱数・クリティカルの乱数)は `game.fight` に置き、魚ごとに作り直す。体力は保存しない。
- `tap(game)` は場面に合わせて「合わせ」「命中/ミス」「再開」を行い、何が起きたかを返す。画面はその返り値で小さな演出を出す。

### 押した時刻とタイミング補正(D-284・D-285・D-289)

- 絵の領域の `pointerdown` の `event.timeStamp`(指が触れた瞬間。performance.now と同じ時計)を、窓口の `tapAt(session, 押した時刻, いまの時刻)` に渡す。窓口は、ゲームの時刻がどこまで進んだか(`clockMs`)を覚えていて、押した時刻まで進めてから `tap` を呼ぶ。ハンドラが遅れて呼ばれても、判定は押した時刻のまま(`tests/input_timing.test.js`)。
- 描画が押した時刻より先に進んでいたときは、`tap(game, backMs)` で、その分だけさかのぼって判定する(いまの場面の中と、前のタップのあとまで。合わせは「!」からの時間、命中は印の位置を、その時刻で計算する)。場面が終わってしまったあと(輪が通り過ぎたなど)はさかのぼれない。
- タイミング補正は窓口だけが知る(計算本体は知らない)。判定 = 押したときに見えていた位置 + 補正。
  - 「+」:タップを `queue` に取っておき、`advanceTo` でゲームの時刻が届いたときに判定する(結果は `onTap` で画面に知らせる)。
  - 「−」:判定は押した時刻のまま。画面が、縮む輪と動く印と制限時間の帯を、補正の分だけ先の位置で描く(`viewLeadMs`)。
- 補正の値は `src/ui/timing.js`(丸め・保存場所・測るときの目安・確かめ用の表示の数)、設定の欄と「測る」は `src/ui/timing_screen.js`。保存場所は `tsuri:timing`・`tsuri:debug-timing`(ゲームの保存とは別)。

### 重い処理の後回し(D-284・D-289)

- 合わせと戦闘の間(掛かった・巻き上げ・体力制)は、保存を後回しにする(`requestSave` が印だけ付け、場面が終わったら `flushSave`)。ページを離れる・隠れる(`pagehide`・`visibilitychange`)ときは、場面によらずすぐ保存する。
- 上の欄(鱗・釣り場・竿の名前・餌のボタン・竿のボタン)は、その場面に入ったときと出たときだけ書き換える。文字は変わったときだけ書き換える(`setText`)。絵の大きさは、大きさが変わったとき(`resize`・ResizeObserver)だけ測る。
- 空と海の背景は、色と大きさが変わらない間、描いた絵を取っておいて写す(`draw.js` の `drawBackground`)。重ね塗りの時間が、1 フレームの描画の大半だった(約 5 ミリ秒のうち 4 ミリ秒)。
- 確かめ:`?debug` のとき、絵の左下に入力の遅れとフレーム間隔(D-286)。ブラウザの自動操作では、`localStorage.setItem` を数えて、合わせと戦闘の間の保存が 0 回であることを確かめる。

### 魚の抽選のしくみ(D-046)

「魚の系統」の乱数(シードから作る)で、1 回の投げごとに 3 つ(強い魚でなければ 2 つ)引く。順番は変えない。

1. 待ち時間:`1.5 秒 + 乱数 × 6 秒`
2. 魚:乱数 u が `strongChance`(0.1)未満なら強い魚、それ以外は弱い魚。区分の中での位置(強い魚なら u ÷ 0.1)を 0〜1 に引きのばし、その値で重みづけで種類を選ぶ。候補は、いまいる釣り場の魚だけ(いちばん新しい釣り場は竿の段階まで、古い釣り場は全段階)。重みは釣り場の最初の段階から 2 倍ずつ(D-275)。
3. ミニゲームの種(強い魚だけ):この値から最初の命中範囲の位置を作り、さらに「ミニゲームの系統」の乱数のシードにする(D-064)。

プレイヤーの操作(合わせ・ミニゲームのタップ・休みからの再開)は、魚の系統の乱数を一切引かない。命中したあとの命中範囲は、ミニゲームの系統から引く。だから、待ち時間と魚の並びは操作によらず同じ。引く回数と順番は Issue #6 から変えていない(出現率が変わったので、並びの中身は変わった:D-113)。

強い魚かどうかは u だけで決まるので、引く数は釣り場によらない。引いた数は投に `raw` として残す(`drawCast` → `resolveCast`)。釣り場を移ったとき(`moveArea`)や、進化で釣り場が変わったときは、投げている・待っている投と取っておいた投を、`raw` のまま新しい釣り場の魚に決め直す(乱数は引き直さない:D-282)。

ヌシ戦は魚の系統を使わない(D-115)。「ヌシに挑む」を押すと、待っていた魚(`game.pendingCast`)を取っておき、`bossSeed(seed, 何回目の挑戦か)` から作ったヌシの投げで戦う。戦いの結果のあとは、取っておいた魚に戻る。だから、ヌシに何回挑んでも、魚の並びは変わらない。

### 戦闘の数値の表とクリティカルの判定(D-078〜D-080)

- 戦闘の数値の表は `{ damage, critChance, critMultiplier, missHeal, timeLimitBonusMs }`。基本の表は `config.combat`。
- `createGame(seed, { combat, critRules })` で表と規則の一覧を渡す。表は `normalizeCombat` で点検・丸めてから `game.combat` に置き、戦闘はこれだけを見る。
- ②-4 の装備は、基本の表をもとに「足す・掛ける」を重ねた新しい表を作り、`createGame`(または付け替えのときに作り直す表)に渡す。戦闘のコードは変えなくてよい。範囲外になっても `normalizeCombat` が丸めるので、戦闘は壊れない。
- 追加クリティカル(D-169):`critStages(context, rules, 上限)` が段数を返す。会心率 c の整数の部分が必ず起きる段数、残りがもう 1 段の確率。ダメージは `hitDamage(表, 段数, 上限)` で「通常ダメージ × 倍率の段数乗」。1 以下なら前の判定と同じ結果。安全上限は `config.combatLimits`(段数 20・総倍率 100 万・ダメージ 10 億)。

### 合わせの輪と、戦闘中の一時的な上乗せ(D-087・D-088・D-186・D-256)

- 輪の数値は、戦闘の数値の表の `hook`(`normal` と `strong` に `ringMs`・`successMs`・`justMs`)。ジャスト倍率(初撃の倍率)は輪ではなく、表の `justMultiplier`(基本 3:D-256)。`normalizeHook` が下限に直す。浮きの装備(②-5)は、ここの `successMs`・`justMs` を広げた表を渡せばよい。
- 判定は `judgeHook(hookTiming(輪), 「!」からの時間)` で、乱数を使わない。遅すぎは時間の進み(`update`)で決まる。
- **表と上乗せの関係**:
  - 表(`game.combat`)は「その日の装備で決まる基本の数値」で、戦闘のあいだは変えない。
  - 上乗せ(`game.fight.boosts`)は「戦闘のあいだだけの一時的な変化」の一覧。1 つは `{ id, when, effects, uses }`。`when`・`effects` は条件発動型の「次の命中に効く」効果(先手・勢い)。旧「ジャストのあとの最初の命中 × 1.5」(`damageMultiplier`)は、初撃に置き換えてなくした(D-256)。命中するたびに `uses` を 1 減らし、0 で消える。戦闘が終わると消え、保存しない(D-186)。
  - 命中のダメージは、下の「条件発動型のスキルと、命中 1 回の計算の順」のとおり。
- **②-4 の特性が同じ仕組みで足せる理由**:条件発動型の特性(「連続で 3 回当てたら、次の一撃 1.3 倍」「合わせがジャストなら、2 回ぶん 1.2 倍」など)は、どれも「ある出来事のときに、上乗せを一覧に足す」で書ける。戦闘のコード(ダメージの計算)は一覧をかけ合わせるだけなので、特性を足しても変えなくてよい。ダメージ以外(回復を減らす など)の上乗せが要るときは、上乗せに項目を足し、計算の 1 か所で使う。

### セーブコードの署名(D-291〜D-297)

- 仕組み:設定で書き出すコードだけに署名を付ける(ブラウザの中の保存は署名なしの `TSURI4-本文-印` のまま)。形は `TSURI5-鍵の番号-保存の版-本文-署名`。署名 = HMAC-SHA256(鍵, 署名の前の `-` までの文字)の先頭 16 バイトを、URL に安全な文字 22 文字にしたもの。計算は Web Crypto(`crypto.subtle`)で、書き出しと読み込みは非同期(設定の画面は結果を待ってから進む)。
- 鍵の置き場:本番の鍵は GitHub の Secrets の `SAVE_SIGNING_KEY`。`pages.yml` の「署名の鍵を書き込む」が、環境変数で `scripts/stamp_key.mjs` に渡し、公開用の `_site/src/save_key.js` だけを書き換える(リポジトリにはコミットしない。記録に値を出さない。GitHub も Secrets の値を記録で隠す)。鍵がないときは公開が失敗し、前の公開が残る。手元・テスト・PR の確かめでは、リポジトリの仮の鍵(dev)を使う。デバッグ用の鍵(debug)も仮の鍵で、`src/ui/save_sign.js` にある。
- 鍵の番号:本番 k1・手元 dev・デバッグ debug。読める鍵の一覧にない番号は拒否する(debug なら「デバッグ用のコードは、本番では読めません」、ほかは「知らない鍵のコードです」)。
- 鍵を替える手順(今回はやらない:D-296):
  1. Secrets に新しい鍵 `SAVE_SIGNING_KEY_K2` を足す(古い `SAVE_SIGNING_KEY` は消さない)。
  2. `save_key.js` を「いまの鍵(k2)」と「読むだけの古い鍵の一覧(k1)」の形にし、`stamp_key.mjs` と `pages.yml` で両方を書き込む。`save_sign.js` の読める鍵の一覧に古い鍵を足す。
  3. 書き出しは k2 になり、k1 のコードも読める。古い鍵を読まなくするときは、決定を足してから一覧から外す。
- 署名なしの拒否(②-5a から:D-324):`config.js` の `saveCode.acceptUnsigned` は `false`。テスト(`tests/signed_code.test.js`)は、true にした設定で古い形式の読み替えも確かめ続ける。ブラウザの中の保存(`parseSave`)は署名なしのまま読むので、影響しない。
- 限界:鍵は公開ページの中にあるので、ページのファイルを読める人は正しい署名を作れる。目的は、チャットの AI などに貼って書き換えさせる手軽な手口を止めることで、本物の不正防止ではない。ブラウザの中の保存データ(開発者の道具で書き換えられる)も守らない。
- 保存の版 5 と署名つきの読み分け(D-307):保存の版が 5 になり、署名なしの形(ブラウザの中の保存)も先頭が `TSURI5-` になった。署名つきは `TSURI5-` の次が鍵の番号(英小文字で始まり、「-」が続く)。署名なしの本文はウロコインの数のあとに「~」が続くので、この形に当たらない。`readSaveCode` は、鍵の番号の形なら署名つきとして、そうでなければ署名なし(注意つき。acceptUnsigned が false なら拒否)として読む。保存の版を 6 に上げるときも同じ決まりで読み分けられる。

### スキルの作りと、スキルを足す手順(D-167・D-195・D-207・D-210)

### 条件発動型・ゲージ系のスキルと、命中 1 回の計算の順(D-184〜D-187・D-191・D-209)

- `refreshCombat` が `game.triggers`(条件ごとの効果の合計:`triggerAmounts`)を作る。戦闘の数値の表(`game.combat`)には入れない。
- 戦闘を始めるとき(`startFight`):先手があれば `{ id: "first-hit", when: "firstHit", effects }` を上乗せに積む。ヌシ戦は合わせの成功とみなす(先手は効き、ジャストではない:D-187)。
- **ジャストの初撃**(`startFight` のあとの `justStrike`:D-256)。強い魚(`cast.kind === "strong"`)をジャストで合わせたときだけ:
  1. ジャスト倍率 = 表の `justMultiplier` + ジャスト・ブースト(`triggers.just.justMultiplier`)に逓減(`effectiveStats` の `justMultiplierCurve`)をかけ、安全上限(`combatLimits.maxJustMultiplier`)で止める。
  2. 初撃 = 表の `damage`(1 命中の基本のダメージ。条件発動型は入れない)× ジャスト倍率を四捨五入し、`maxHitDamage` で止める。クリティカルの乱数は引かない。
  3. 実効防御(表の貫通に逓減をかけたもので計算)で減らす(`strikeDamage`。最小 1)。
  4. 体力から引く。命中・連撃・クリティカルの数には入れない。上乗せ(先手)は消さないので、初撃のあとの最初の命中に乗る。先制は体力が減ったので効かない。
  5. 体力が 0 なら `finish(CAUGHT, "strike")`(ミニゲームなし)。結果と合わせのタップの返り値に `strike`(ダメージ・防御の前・倍率・残りの体力・釣れたか)を入れる。
- 命中のたび(`fightTap` → `triggeredStats`):
  1. 満たしている条件を集める:連撃(段数 = それまでに続けて命中した数。最大 `config.skills.comboMax`)、上乗せに積んだ条件(先手・勢い)、満タンで最初の命中まで(先制)、体力が 25% 以下(とどめ)。
  1.5 芯・縁:命中した位置を `zoneBand(位置, 命中範囲, config.skills)` で 芯・通常・縁 に分ける(中心からの距離が 0.3 以下なら芯、0.75 以上なら縁。乱数は使わない)。芯なら芯の効果(会心率)、縁なら縁の効果(ダメージ%)を足す。
  2. 基本のダメージ =(表の通常ダメージ + 足す量の合計)×(1 + 割合の合計:とどめ + 縁)を四捨五入(最小 1、安全上限まで)。会心率 = 表 + 足す量の合計(安全上限まで)。貫通 = 表 + 連撃・貫 × 段数。
  2.5 会心率・倍率・貫通の合計に逓減をかける(`combat.js` の `effectiveStats`。形は `formula.js` の `softCurve`、数は `config.formula`:D-255・D-260)。
  3. クリティカルの乱数を 1 回引き、段数を決める(`critStages`。100% をこえると追加クリティカル)。
  4. ダメージ = 基本のダメージ × 倍率の段数乗(四捨五入)。ジャストの倍率は命中には掛けない(初撃だけ)。
  4.5 防御で減らす:実効防御 = 魚の防御(`cast.minigame.defense`)− 貫通(下限 0:`effectiveDefense`)。ダメージ = max(1, 丸め(ダメージ ×(1 − 実効防御)))、実効防御 100% 以上はいつも 1(`defendedDamage`:D-235)。結果に `effDefense`・`rawDamage`・`defended` を入れる(画面の色分けに使う)。
  5. 上乗せの残り回数を 1 減らす。クリティカルなら、勢いを上乗せに積む。連撃の段数を 1 増やす。ミスなら連撃を 0 に戻す。
- 条件発動型が 1 つもないときは、表をそのまま使う(前と同じ結果)。
- ゲージの芯・縁の色分けは `fight_view.js` の `gaugeBands`(芯か縁のスキルを付けているときだけ帯の割合を返す)、命中したときの「芯」「縁」は `effects.js` の `bandLabel`。
- 画面の小さな表示は `src/ui/fight_view.js` の `fightBadges`(連撃 ×n、次の命中で効く条件の名前)と `defenseBadge`(防御と実効防御。100% 以上は赤)。

### 防御とヌシ戦の長さの確かめ方(D-254・D-260)

- 魚の防御・体力・制限時間は `formula.js`(`fishDefense`・`fishHp`・`fishTimeLimitMs`)。ヌシの体力は「目標の命中回数 × 基準の装備の 1 命中の期待ダメージ(`bossReferenceDamage`)×(1 − 基準の実効防御:`bossReferenceDefense`。基準の貫通は N(g) が少ないほど低い)× 補正」。5 体目の下限は `noPenetrationFloor`(貫通なしで押せる回数)。補正(`config.formula.bossReference`)は、下の重いテストで命中回数が目標に入るように合わせた数。スキルや装備の数値を変えたら、重いテストで確かめ直し、ずれたら補正を合わせ直す。
- 装備の組み立てと戦闘のシミュレーションは `tests/slow/builds.js`:
  - 平均的な装備:レア・グレード g・値は真ん中・スキルなし。
  - 育てた装備(6 枠:D-322・D-327):段階 g のクレートから 3 × N(g) 個(N(g) = 10 × g^0.5 を `formula.js` の `referenceDraws`。枠が 6 つでも引く数は 3 枠のときと同じ)をガチャの種で引き、種類ごとに分けて候補にする。値と、命中回数に効くスキルのレベルが全部ほかの候補以下のものは除く。糸・リール・ルアーの全部の組み合わせを 1 シードで比べて、良い 10 通りを 3 シードで比べ直し、次におもり・浮き・おまもりを 1 枠ずつ(3 シードで一番良いもの)、最後に 6 枠を 1 周見直す。測るときは、ガチャの種 15 個(D-262)× 戦闘のシード 5 つの中央値の中央値。

## GitHub のテストの流れ

設定は `.github/workflows/ci.yml` の 1 つです。

| いつ | 回るもの |
| --- | --- |
| PR を出した・更新したとき | 速いテストと型チェック。計算本体(`src/core/`)などが変わったときだけ重いテストも(D-005・D-028・D-150)。 |
| main に取り込んだあと | 速いテストと型チェック(版は 1 つ)。 |
| 手動(Actions の画面の「Run workflow」) | 重いテスト。 |

公開は `.github/workflows/pages.yml` で、テストとは別に動きます(D-052)。

| いつ | 動くもの |
| --- | --- |
| main に取り込んだあと | `index.html` と `src/` を GitHub Pages に公開する。 |
| 手動(Actions の画面で「pages」を選び「Run workflow」) | 同じく公開する。 |

- Pages の設定(Settings → Pages の Source を「GitHub Actions」)が済む前は、公開の手順を飛ばして成功で終わる。

- 同じ PR を出し直したときは、古い実行を止める(concurrency:同時に走る実行のまとめ役の設定)。
- 最後の `ci-result` ジョブが、ほかの結果をまとめる(D-015)。
- 速いテストは `node --test` がファイルごとに並列で回す。テストは外部の部品を使わないので `npm install` の待ちもない。
- 型チェックは別のジョブで、`npm ci`(`package-lock.json` の版どおりに入れる)のあと `npm run typecheck`(`tsc -p tsconfig.json`)を回す(D-150)。
