# クラウド保存(Google 経由)の調査メモ

> **やめた案(D-329)**:クラウド保存の実装は取りやめた。この調査メモは記録として残す。パソコンとスマホの引き継ぎは、セーブコードの手動の書き出しと読み込みで行う。共有ボタンも外した(D-330)。

クラウド保存を作る前に、方式・Google 側の条件・オーナーの作業・競合の扱い・段取りを調べたメモです(D-310・D-312)。この依頼ではコードを変えていません。実装は、このメモを見て決めます。

- 調べた日:2026-10-07
- 方針(D-310):Google 経由。自分(オーナー)だけが使える隠し入口。署名つきセーブコード(`TSURI5-…`)をそのまま置く。?debug のときはクラウドに触らない。競合は「どちらが新しいか」を見せて選ぶ。最初は手動の保存と読み込み。

## 0. 確かめ方と、確かめられなかったこと

- この作業環境からは、Google の説明のページ(developers.google.com・support.google.com)を直接開けませんでした(作業環境の通信の決まりで止められた)。
- そのため、**検索の結果に出た公式ページの抜き出し**で確かめました。各条件に、元の公式ページの URL を書いています。
- 抜き出しで確かめられなかった点は、「**確認できなかった**」として 9 章にまとめ、推測では埋めていません。
- Google の画面の名前や条件は、よく変わります。実装の依頼の最初に、出典のページを開いて、もう一度確かめます(D-312)。

用語:

| 用語 | 意味 |
| --- | --- |
| OAuth(オーオース) | 「このアプリに、自分の Google のデータの一部を使わせてよいか」を、パスワードを渡さずに許可する仕組み。 |
| スコープ | 許可の範囲。今回は「このアプリ専用の、見えない置き場だけ」(`drive.appdata`)。 |
| アクセストークン | 許可を受けたしるしの、短い期間だけ使える合言葉の文字列。これを付けて Drive に読み書きする。 |
| 更新用の許可(リフレッシュトークン) | アクセストークンが切れたとき、ログインの操作なしで新しいものをもらうための、長く使える合言葉。 |
| 同意画面 | 「このアプリに〇〇を許可しますか」と Google が出す画面。テスト中は「確認されていないアプリ」の注意も出る。 |
| クライアント ID | アプリを Google に名乗るための番号(公開してよい値)。 |
| クライアント シークレット | サーバーで使う秘密の値。**今回は使わない**。 |

## 1. 方式の比較

| 比べる点 | A:Google ドライブのアプリ専用の置き場(appDataFolder) | B:Firebase(Google のログイン+Firestore) | C:クラウドを使わない(共有メニュー・クリップボード) |
| --- | --- | --- | --- |
| 必要な許可 | `drive.appdata`(このアプリ専用の、見えない置き場だけ)。「推奨・機微でない」スコープ(2 章の 2) | Google のログイン(名前とメール)だけ。データは Firebase 側の DB に置く | なし |
| オーナーの作業 | Google Cloud でプロジェクト・Drive API・同意画面・テストユーザー・クライアント ID(3 章)。1 回だけ、30 分ほどの見込み | Firebase のプロジェクト・ログインの設定・Firestore の作成・**セキュリティルールの作成**(自分だけが読み書きできる決まり)・承認済みドメイン | なし |
| 無料の範囲 | Drive API は標準の使い方なら追加の費用なし。1 日の上限(4 億単位)までは課金されない(2 章の 5)。容量は自分のドライブの容量(数十 KB) | Spark(無料)プランで Firestore 1 GiB・読み 5 万回/日・書き 2 万回/日(2 章の 6)。こえると、その月は止まる | 費用なし |
| ログインの有効期間 | アクセストークンは短い(1 時間ほどの見込み。9 章)。切れたら、ボタンを押してもう一度許可をもらう。テストの状態では、許可そのものが 7 日で切れる(2 章の 1) | Firebase のログインは、ブラウザに残れば続く見込み(Firebase の説明で確かめていない:9 章) | なし |
| 端末間の同期 | 同じ Google アカウントなら、どの端末からも同じファイルを読み書きできる | 同じ | 手で、コードを送って貼る |
| 実装の重さ | 中。Google の小さな部品(GIS)を 1 つ読み込み、Drive の REST(決まった URL への読み書き)を `fetch` で呼ぶ。ビルドなしで書ける | 重い。Firebase の部品(SDK)を読み込み、セキュリティルールを書いて確かめる。Safari ではログインの方式に注意が要る(2 章の 6) | 軽い。いまの「コピー」に「共有」を足すだけ |
| リポジトリが公開でも安全か | 安全。クライアント ID は公開してよい値で、ブラウザで動くアプリはシークレットを使わない(2 章の 3)。承認済みの生成元(https://yuusukekokubu-a11y.github.io)以外では使えない | 安全。Firebase の API キーはコードに書いてよい値。守りはセキュリティルールで行う(2 章の 6)。ルールを間違えると、誰でも読み書きできてしまう | 安全 |
| 失敗したときの動き | オフライン:保存も読み込みもできない(エラーを出し、ブラウザの中の保存はそのまま)。トークンの失効:もう一度ボタンで許可をもらう。容量:セーブコードは 1.2 万文字ほどなので、事実上問題にならない | オフライン:Firestore にはオフラインのしくみがあるが、今回は使わない見込み。ルールの間違い・上限こえ:止まる | 端末の共有メニューやメモのアプリしだい |
| 自分だけで使う形との相性 | よい(テストユーザーに自分だけを入れる) | よい(ルールで自分の ID だけを許す) | よい |

ほかの方式も考えましたが、次の理由で外しました。

- **Google スプレッドシートや Apps Script**:置き場としては使えますが、許可の範囲が広くなる(シート全体)か、Apps Script を別に公開する作業が増えます。
- **GitHub の Gist など**:Google 経由という方針(D-310)から外れます。

## 2. Google 側の条件

各項目の「確かめた範囲」の欄:

- **抜き出し**:検索の結果に出た、公式ページの抜き出しで確かめた。
- **一部**:一部だけ確かめた。
- **未確認**:確かめられなかった(9 章)。

### 2.1 同意画面の「テスト」の状態の制限

- テストの状態では、テストユーザーは **100 人まで**。同意画面に登録した人だけが使える。
- テストユーザーの許可は、**同意した時から 7 日で切れる**。ただし、名前・メール・プロフィールだけを求めるアプリは例外。`drive.appdata` を求める今回のアプリは、この例外に当たらない。
- 更新用の許可(リフレッシュトークン)を受け取った場合も、**7 日で切れる**。
- 確かめた範囲:抜き出し
- 出典:
  - Manage App Audience(Google Cloud のヘルプ):https://support.google.com/cloud/answer/15549945
  - Using OAuth 2.0 to Access Google APIs:https://developers.google.com/identity/protocols/oauth2
  - (同じ内容)Set up Google Cloud and OAuth:https://developers.google.com/health/setup

### 2.2 公開(本番)にする条件と、審査の要否

- `drive.appdata` は、Drive のスコープの表で「**推奨・機微でない(Recommended, Non-sensitive)**」に分けられている。
- 機微でないスコープは、いちばん簡単な確認(basic app verification)だけでよい、とされる。
- 確かめた範囲:一部。「機微でない」の分類は抜き出しで確かめた。本番にするときの具体的な手順と、確認にかかる日数は未確認(9 章)。
- 出典:
  - Choose Google Drive API scopes:https://developers.google.com/workspace/drive/api/guides/api-specific-auth
  - When is verification not needed(Google Cloud のヘルプ):https://support.google.com/cloud/answer/13464323
  - OAuth app state overview:https://developers.google.com/identity/protocols/oauth2/production-readiness/overview
- 今回の見方:自分だけが使うので、**テストの状態のまま**でよい。7 日ごとに許可が切れても、手動の保存と読み込みなら、ボタンを押したときにもう一度許可すればすむ。

### 2.3 ブラウザだけで完結する形と、クライアント ID の扱い

- **ブラウザだけで動く形**:Google Identity Services(GIS)の「トークンの方式」(`google.accounts.oauth2.initTokenClient`)を使う。サーバーは要らない。
  - 確かめた範囲:抜き出し
  - 出典:Use the token model:https://developers.google.com/identity/oauth2/web/guides/use-token-model
- **トークンが切れたとき**:アクセストークンは短い期間だけ使える。切れたら、**利用者の操作(ボタンを押すなど)から `requestAccessToken()` を呼んで**、新しいものをもらう。
  - つまり、ページを隠すときなどの自動の操作だけでは、新しいトークンをもらえない。
  - 確かめた範囲:抜き出し
  - 出典:同上
- **画面を省く呼び方**:`prompt` を空の文字にすると、許可済みの人には、アカウントを選ぶ画面と同意画面を出さずに済む(「既にある session(ログインの続き)」のとき)。
  - それでも小さな窓(ポップアップ)が一瞬開くかは、確かめられなかった(9 章)。
  - 確かめた範囲:抜き出し
  - 出典:Google Account Authorization JavaScript API reference:https://developers.google.com/identity/oauth2/web/reference/js-reference
- **更新用の許可(リフレッシュトークン)**:トークンの方式では、受け取れない見込み。
  - 確かめた範囲:一部。公式ページでは「切れたら利用者の操作でもう一度もらう」と書かれていることだけを確かめた。「受け取れない」とはっきり書いた公式の文は確かめられなかった(9 章)。
  - 長く使える許可は「コードの方式」(`initCodeClient`)で受け取るが、これはサーバーで秘密の値を使うので、今回の形(サーバーなし)では使わない。
- **承認済みの JavaScript の生成元**(このアプリを使ってよいサイトのアドレス)の決まり:
  - `https://` で始める(手元の確かめ用の `http://localhost` は例外)。
  - IP アドレスは使えない。
  - 後ろに道筋(`/fish/` など)を付けない。
  - 確かめた範囲:抜き出し
  - 出典:OAuth 2.0 for Client-side Web Applications:https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow
- **クライアント シークレット**:ブラウザで動くアプリは、クライアント シークレットを使わない(使う必要がない)。
  - 確かめた範囲:抜き出し
  - 出典:同上、Setup(Get your Google API client ID):https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid
- まとめ:**ボタンを押すたびに、もう一度許可をもらう前提で作る**。
  - 1 回の遊びの中で、トークンが生きている間は、続けて使える。
  - 7 日ごと(テストの状態)には、同意画面がもう一度出る。

### 2.4 スマホ(iPhone の Safari・Android の Chrome)

- Google のログインの部品(GIS)は、iPhone の Safari と、Android・iPhone の Chrome に対応している。
- アプリの中の簡易ブラウザ(WebView)では、ログインできない。
- Safari などでは、追跡を防ぐしくみ(ITP)のため、ログインの流れがポップアップ(小さな窓)に変わることがある。
- 確かめた範囲:抜き出し
- 出典:
  - Supported browsers and platforms:https://developers.google.com/identity/gsi/web/guides/supported-browsers
  - Understand the One Tap user experience:https://developers.google.com/identity/gsi/web/guides/features
- **確かめられなかったこと(9 章)**:
  - ホーム画面に追加して、全画面で開いたとき(iPhone の「ホーム画面に追加」)に、ポップアップがどう開くか(別の Safari の画面に移るか、戻ってこられるか)。
  - トークンの方式のポップアップが、iPhone の Safari で正しく閉じて結果を返すか。
  - これらは、実装の依頼の最初に、オーナーの iPhone で試すのが確実。

### 2.5 Drive API の無料の範囲と容量

- 標準の使い方は、**追加の費用なし**。
- 上限:1 分あたり 1 プロジェクト 100 万単位、1 利用者 32.5 万単位。
- 1 回の重さ:読む 5 単位・一覧 100 単位・ダウンロード 200 単位・更新 50 単位。
- 1 日 4 億単位の境目までは課金されない。
- 上限をこえた分を課金する予定が「2026 年の後半」と書かれている。今回の使い方(1 日に数十回)は、上限より何けたも少ない。
- 確かめた範囲:抜き出し
- 出典:Usage limits(Drive API):https://developers.google.com/workspace/drive/api/guides/limits
- **アプリ専用の置き場(appDataFolder)のしくみ**:
  - 見えない置き場で、このアプリだけが読み書きでき、利用者や、ほかのアプリからは見えない。
  - 初めてファイルを作ったときに、自動でできる。
  - 利用者がアプリの接続を外すと消える。利用者が手で消すこともできる。
  - 確かめた範囲:抜き出し
  - 出典:Store application-specific data:https://developers.google.com/workspace/drive/api/guides/appdata
- **容量**:アプリ専用の置き場のファイルが、利用者のドライブの容量に数えられるかは、確かめられなかった(9 章)。
  - セーブコードは最大でも 1.2 万文字(約 12 KB)。バックアップを入れても 2〜3 ファイル(数十 KB)なので、どちらでも問題にならない。

### 2.6 Firebase(B 案)の条件

- **無料の範囲**:無料の Spark プランで、Firestore 1 GiB・読み 5 万回/日・書き 2 万回/日・消す 2 万回/日。
  - 上限をこえると、その月は、その機能が止まる。
  - 出典:Firebase pricing plans:https://firebase.google.com/docs/projects/billing/firebase-pricing-plans、Understand Cloud Firestore billing:https://firebase.google.com/docs/firestore/pricing
- **API キー**:Firebase の API キーは、コードや公開する設定ファイルに書いてよい。
  - 守りは、セキュリティルール(誰が読み書きできるかの決まり)と App Check で行う。
  - 出典:Learn about and manage API keys for Firebase:https://firebase.google.com/docs/projects/api-keys
- **Safari などでのログイン**:Safari 16.1 以降(と Chrome M115 以降)では、移動して戻る形のログイン(`signInWithRedirect`)に、追加の対応が要る(ポップアップの形に変える、など)。
  - 出典:Best practices for using signInWithRedirect on browsers that block third-party storage access:https://firebase.google.com/docs/auth/web/redirect-best-practices
- 確かめた範囲:抜き出し

### 2.7 共有メニュー(C 案)の条件

- 共有メニュー(Web Share API・`navigator.share`)で、文字を共有できる。
  - 呼べるのは、ボタンを押したときなどの利用者の操作の中だけ。
  - 共有できるかは、先に `navigator.canShare` で確かめる。
- 確かめた範囲:抜き出し
- 出典:Web Share API(MDN):https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API、Navigator: share() method:https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share
- iPhone の Safari と Android の Chrome で、文字の共有が使えるか(対応表):確かめられなかった(9 章)。

## 3. オーナーの作業の手順書(A 案)

Google Cloud の画面(https://console.cloud.google.com/ )で、パソコンのブラウザから行います。30 分ほどの見込みです。

- **画面の名前について**:同意画面まわりは、2025 年ごろから「Google Auth Platform」(ブランディング・対象・クライアント・データアクセス)という新しい画面に変わっています(上の出典のヘルプの題名「Manage App Audience」「Manage OAuth App Branding」から)。このため、画面の名前が下の手順と少しちがうことがあります。その場合は、いちばん近い名前を選んでください。
- **困ったとき**:迷ったら、画面の写真ではなく、画面の上の題名と、ボタンの文字を教えてください。

### 手順

1. **プロジェクトを作る**
   1. 画面の上の、プロジェクトの選択(「プロジェクトを選択」または今のプロジェクトの名前)を押す。
   2. 「新しいプロジェクト」を押す。
   3. 「プロジェクト名」に `tsuri-cloud` などを入れて、「作成」を押す。
   4. 作ったプロジェクトが選ばれていることを、画面の上で確かめる。
2. **Drive API を有効にする**
   1. 左のメニュー(☰)→「API とサービス」→「ライブラリ」を開く。
   2. 検索に `Google Drive API` と入れて選ぶ。
   3. 「有効にする」を押す。
3. **同意画面(Google Auth Platform)を作る**
   1. 左のメニュー →「API とサービス」→「OAuth 同意画面」(または「Google Auth Platform」)を開く。
   2. 「開始」(または「同意画面を構成」)を押す。
   3. 「アプリ情報」:アプリ名(例:`つり`)、ユーザー サポートメール(自分の Gmail)を入れる。
   4. 「対象」:**外部**を選ぶ。
   5. 「連絡先情報」:自分の Gmail を入れる。
   6. 規約に同意して「作成」を押す。
4. **使う範囲(スコープ)を足す**
   1. 「データアクセス」(または「スコープ」)を開く。
   2. 「スコープを追加または削除」を押す。
   3. 一覧から `.../auth/drive.appdata`(説明:「Google ドライブ内の独自の構成データの参照と管理」に近い文)にしるしを付ける。
   4. 「更新」を押し、「保存」を押す。
   5. **ほかのスコープ(`drive` や `drive.file` など)は選ばない。**
5. **テストユーザーに自分を足す**
   1. 「対象」(または「OAuth 同意画面」)を開き、「公開ステータス」が「**テスト**」であることを確かめる。
   2. 「テストユーザー」→「ユーザーを追加」(Add users)を押す。
   3. 自分の Gmail のアドレスを入れて「保存」を押す。
   4. **「アプリを公開」(本番にする)は押さない。**
6. **OAuth クライアント ID を作る**
   1. 「クライアント」(または「API とサービス」→「認証情報」→「認証情報を作成」→「OAuth クライアント ID」)を開く。
   2. 「アプリケーションの種類」:**ウェブ アプリケーション**を選ぶ。
   3. 「名前」:`tsuri-web` など。
   4. 「承認済みの JavaScript 生成元」の「URI を追加」を押し、`https://yuusukekokubu-a11y.github.io` と入れる。
      - 最後の `/` と `/fish/` は付けない。
      - 手元で試すなら、`http://localhost:8000` も足してよい。
   5. 「承認済みのリダイレクト URI」は空のままでよい。
   6. 「作成」を押す。
7. **クライアント ID を Code に渡す**
   1. 作成のあとに出る「クライアント ID」(`…apps.googleusercontent.com` で終わる長い文字)をコピーする。
   2. 実装の依頼文に貼る。これは**公開してよい値**です。リポジトリの設定ファイル(例:`src/cloud_config.js`)に置きます。

### 秘密の値の注意

- 作成のときに「**クライアント シークレット**」も表示されることがあります。
  - これは**使いません**。
  - リポジトリにも、チャット(依頼文)にも、**貼らないでください**。
  - JSON のダウンロードも要りません。
- 「秘密」「secret」と書かれた値は、すべて同じ扱いです。
- GitHub の Secrets(署名の鍵)には、何も足しません。クライアント ID は公開してよい値なので、Secrets は使いません。
- もし、まちがってシークレットを貼ってしまったら、Google Cloud の「クライアント」の画面で、そのシークレットを無効にして作り直してください(Code に知らせてください)。

## 4. 競合の扱いの案

### 4.1 何を「新しい」とするか

候補の比べ:

| 指標 | よい点 | 弱い点 |
| --- | --- | --- |
| 保存した時刻 | 分かりやすい(「10 月 7 日 21:05」) | 端末の時計がずれていると誤る。「古い端末で長く遊んだ」と「新しい端末で少し遊んだ」を区別できない |
| 通算の遊び回数 | 進んだ量が分かる | いまの保存には「遊んだ回数」の欄がない(足すと保存の版が上がる) |
| 進行度の指標(竿の段階・工程・ガチャの回数・釣れた魚の数) | いまの保存の中身だけで出せる | 「ウロコインだけ増えた」などは比べにくい |

案:

- **何で決めるか**:「新しい」は**保存した時刻**で決める。クラウドのファイルの更新時刻(Drive が付ける時刻)と、ファイルの中に書いた時刻の両方を持つ。
- **選ぶ画面に出すもの**:両方の**進行度の要約**(竿の段階・ウロコイン・ガチャの回数・端末の名前)を並べ、人が目で比べて選ぶ。
- **「両方が進んでいる」の見つけ方**:端末の中に「最後にクラウドと合わせたときの印」(時刻とセーブコードの要約)を覚えておく。そのあとで、クラウド側と端末側の**両方**が変わっていたら、「両方が進んでいます」として選ぶ画面を出す。

### 4.2 選ぶ画面の案(簡素)

```
クラウドと、この端末の記録がちがいます

  クラウド  10/07 21:05 保存(iPhone)
            港 段階 5・ウロコイン 1.2万・ガチャ 120 回
  この端末  10/07 20:40 保存
            港 段階 4・ウロコイン 3.4万・ガチャ 90 回
  (両方が、前に合わせたあとに進んでいます)

  [クラウドを読み込む]  [この端末で上書き]  [やめる]
```

- 新しいほうに「新しい」の札を付ける。
- 押したあとに、もう一度だけ確認を出す。

### 4.3 上書きの事故を防ぐ工夫

- **クラウドを上書きする前**:クラウドの今のファイルを 1 世代だけ、バックアップ(`tsuri-save.prev`)に写す。
- **端末を上書きする前**:端末の今のセーブコードを、ブラウザの別の保存場所(例:`tsuri:cloud-backup`)に 1 世代だけ残す。
- **戻す画面**:隠し入口の画面に「1 つ前に戻す」を置く(2 つ目の依頼で)。
- **確認**:読み込みは、いまの読み込みと同じく、上書きの確認を出す。

## 5. 置くものの詳細

- **ファイルの中身**:アプリ専用の置き場(appDataFolder)に、JSON(決まった形の文字)のファイルを 1 つ置く。
  - ファイル名:`tsuri-save.json`
  - バックアップ:`tsuri-save.prev.json`

```json
{ "format": 1, "savedAt": "2026-10-07T12:05:00Z", "device": "iPhone", "summary": { "rodStage": 5, "coins": 12000, "draws": 120 }, "code": "TSURI5-k1-5-…" }
```

- **code**:設定の「書き出し」と同じ、署名つきセーブコード(`TSURI5-k1-5-…`)。
- **summary**:選ぶ画面に出す要約だけ。読み込みでは使わない。
- **大きさ**:持ち物 100 個・鱗 20 種類で、セーブコードは約 2100 文字。魚 300 種類を全部持っても約 1.1 万文字。JSON の枠を入れても 12 KB ほど。
- **読み込み**:いまの読み込み(`readSaveCode`。署名の確認を含む)をそのまま使う。
  - 署名が合わない・知らない鍵・デバッグ用のコードは、いまと同じ文で拒否する。
  - 上書きの確認を出す。
- **署名の鍵の番号が変わったとき**:
  - 鍵を替えるときは、古い番号も読める形にする決まりがある(DESIGN の「鍵を替える手順」)。そのため、クラウドの古いコード(k1)も読める。
  - 古い番号を読まなくする前に、クラウドのファイルを新しい鍵で保存し直すよう案内する。
- **署名なしの古い形式の拒否(②-5)との関係**:クラウドには、いつも署名つきのコードを置くので、影響はない。
  - クラウドより前に書き出した TSURI1〜4 のコードは、クラウドには置かない(置く前に、いまの形で書き出し直す)。
- **?debug のとき**:クラウドに触らない(読みも書きもしない)。
  - デバッグ用の別のファイルは作らない。テスト用の Google のプロジェクトを分ける手間に見合わないため。
  - デバッグの確かめは、手元の偽物の置き場(テスト用の作り物)で行う。

## 6. 隠し入口の案

案 1(すすめる):**バージョン表示を 3 秒の間に 7 回押す**と、その端末で「クラウド」を出す。

- 押す場所:釣りの画面の右下のバージョン表示(`v0.23.0・abc1234`)。
- 覚える場所:ブラウザの別の保存場所(例:`tsuri:cloud-enabled`)。ゲームの保存とセーブコードには入れない。
- 出るもの:設定の画面に「クラウド」の欄。中身は、ボタン 3 つと文字だけ(見た目は簡素):
  - 状態の文(例:「未接続」「前回の保存:10/07 21:05」)
  - 「クラウドに保存」「クラウドから読み込む」
  - 「クラウドの表示を消す」
- 使えない場面:?debug のときは、欄を出さない(押しても出ない)。

案 2:`?cloud` を付けて開いたときだけ出す。

- URL の指定の表(`URL_PARAMS`)と、SPEC の「確認用の仕組みの一覧」に 1 行足す。
- 欠点:スマホでは、URL に毎回付けるのが手間になる。ホーム画面に追加した場合は、追加したときの URL に付ける必要がある。

すすめる理由:

- 案 1 は、1 回押せば、その端末で出続ける。
- ?debug と同じく、URL の指定の表を増やさずに済む。

## 7. 段取りと見込み

| 依頼 | 中身 | 所要時間の見込み | 危険と対策 |
| --- | --- | --- | --- |
| 1. 手動の保存と読み込み | 隠し入口・クライアント ID の設定ファイル・GIS の読み込み・トークンの取り方(ボタンから)・Drive の読み書き(`fetch`)・状態の文・?debug では触らない・テスト(偽物の置き場) | 実装 3〜4 時間+オーナーの iPhone での確かめ | 小さな窓が止められる(ボタンの中で呼ぶ)/トークンの失効(もう一度押してもらう)/オフライン(エラーの文。ブラウザの中の保存は変えない)/iPhone でホーム画面から開いたときの動き(最初に確かめる) |
| 2. 競合の画面とバックアップ | 最後に合わせた印・「両方が進んでいます」の画面・1 世代のバックアップと戻す | 実装 2〜3 時間 | 端末の時計のずれ(要約も見せて人が選ぶ)/まちがった上書き(バックアップ) |
| 3. 自動の保存 | ページを隠すとき・竿が進んだときなどに、トークンが生きていれば保存する(切れていれば何もしない。小さな窓は出さない) | 実装 2 時間 | トークンが 1 時間ほどで切れるので、自動で保存できるのは、ボタンで許可をもらってからの間だけ/ページを閉じる途中で通信が切れる(次の起動で、未保存を知らせる) |

- テストは、Google に本当につながずに、偽物の置き場(`fetch` を差し替えたもの)で行う。CI でもそうする。本物の確かめは、オーナーの端末で行う。
- 依頼 1 の前に、オーナーの作業(3 章)が済んでいる必要がある。

## 8. 推奨案と、実装の依頼文の叩き台

### 推奨案

**A(Google ドライブのアプリ専用の置き場+GIS のトークンの方式)を、テストの状態のまま使う。** 理由:

- 許可の範囲が「このアプリ専用の置き場だけ」と最も狭く、機微でないスコープ。
- サーバーが要らない。GitHub Pages(いまの公開)のまま動く。
- クライアント ID は公開してよい値なので、いまのリポジトリの形(公開)で問題がない。
- Firebase(B)より部品が少なく、守りのルールを書きまちがえる危険がない。
- 弱い点は、ボタンを押すたびに許可を取り直す場面があること、テストの状態では 7 日ごとに同意し直すこと。これらは、手動の保存と読み込みなら、自分だけで使う範囲では困らない見込み。

あわせて、**C(共有メニュー)を小さく足す**ことも考えられます。いまの「コピー」の横に「共有」を置くだけで、Google がつながらないときの逃げ道になります。

### 実装の依頼文の叩き台(依頼 1)

```
依頼名:クラウド保存(Google ドライブ)の手動の保存と読み込み

【0】
- 方式は A(drive.appdata・GIS のトークンの方式)。Google 側はテストの状態のまま。
- クライアント ID:(オーナーが貼る。公開してよい値)。src/cloud_config.js に置く。
- 隠し入口:バージョン表示を 3 秒の間に 7 回。?debug のときはクラウドに触らない。

【作るもの】
(a) 設定の「クラウド」の欄(隠し入口で出す):状態の文、「クラウドに保存」「クラウドから読み込む」「クラウドの表示を消す」。
(b) 保存:ボタンから許可をもらい(トークンが生きていれば省く)、appDataFolder の tsuri-save.json に、署名つきセーブコードと時刻・要約を書く。前のファイルは tsuri-save.prev.json に写す。
(c) 読み込み:ファイルを読み、いまの読み込み(署名の確認)を通し、上書きの確認を出す。端末の今のコードは tsuri:cloud-backup に 1 世代残す。
(d) 失敗の文:オフライン・許可を断られた・トークンの失効・ファイルがない。
(e) テスト:fetch を差し替えた偽物の置き場で、保存・読み込み・失敗・?debug で触らないことを確かめる。

【受け入れ条件】
1. オーナーの iPhone(Safari・ホーム画面から)と Android の Chrome で、保存と読み込みができる(オーナーが確かめる)。
2. 署名が合わないファイルは拒否し、いまのデータは変わらない。
3. ?debug のとき、Google の部品を読み込まない・通信しない。
4. クライアント シークレットなど、秘密の値がリポジトリにない。

【やらないこと】
競合の画面、自動の保存、Firebase、本番(公開)への切り替え。
```

依頼 2(競合の画面とバックアップ)と依頼 3(自動の保存)は、依頼 1 を遊んで確かめたあとに、7 章の中身で依頼文を作ります。

## 9. 確認できなかった点

| 点 | 何が分からないか | どう確かめるか |
| --- | --- | --- |
| 公式ページの直接の確認 | この作業環境から Google のページを開けなかった。上の条件は、検索の結果の抜き出しで確かめた | 実装の依頼の最初に、出典のページを開いて読み直す |
| アクセストークンの有効時間 | 「短い」とは確かめたが、何分かの公式の数字は確かめられなかった(一般には 1 時間と言われる) | トークンの返り値の `expires_in` を見る |
| トークンの方式で更新用の許可を受け取れないこと | 公式の文で「受け取れない」とはっきり書かれているのは確かめられなかった | Use the token model のページを読む |
| `prompt` を空にしたときの小さな窓 | 画面を省けても、小さな窓が一瞬開くか、iPhone で閉じて戻ってくるか | オーナーの iPhone で試す |
| ホーム画面に追加したときの動き | iPhone で全画面で開いたとき、小さな窓が開くか・戻れるか | オーナーの iPhone で試す |
| 本番(公開)にするときの手順と日数 | 機微でないスコープの「簡単な確認」の中身と日数 | 本番にすると決めたときに、ヘルプを読む(いまはテストの状態のまま) |
| アプリ専用の置き場の容量の数え方 | 利用者のドライブの容量に数えられるか | 影響が小さい(数十 KB)ので、確かめなくても困らない |
| Firebase のログインの続く期間 | 端末に残る期間 | B を選ぶときに確かめる |
| 共有メニューの対応表 | iPhone の Safari と Android の Chrome で文字の共有が使えるか | C を足すときに、実機で確かめる |
| Google Cloud の画面の名前 | 新しい「Google Auth Platform」の画面の、ボタンの正確な名前 | オーナーが作業するときに、画面の名前を教えてもらい、手順書を直す |
